# Копии, восстановление и смена ключа

Всё ценное в боте — в двух местах: база (токены площадок, позиции,
история) и `GIFT_SECRET_KEY` в `.env`. Токены в базе зашифрованы этим
ключом, поэтому **база без ключа бесполезна, а ключ без базы бесполезен**.
Держать их нужно вместе, а копию — отдельно от сервера.

---

## 1. Копии делаются сами

Установщик ставит таймер:

```
systemctl status gift-backup.timer      # когда следующий запуск
systemctl list-timers gift-backup       # расписание
```

Каждую ночь в 03:30 UTC (плюс случайная задержка до 10 минут, чтобы
не совпадать с другими задачами) снимается копия в
`/var/lib/gift/backups/ГГГГММДД-ЧЧММСС/`:

| Файл | Что внутри |
|---|---|
| `db.dump` | дамп PostgreSQL (`pg_dump --format=custom`) |
| `env` | весь `.env`, включая `GIFT_SECRET_KEY` |
| `sessions/` | файлы сессий Telegram — иначе после восстановления придётся заново входить по SMS |
| `manifest` | что и откуда скопировано |
| `SHA256SUMS` | контрольные суммы |

Хранятся последние 14 копий, старые удаляются.

Копия проверяется сразу после создания: дамп читается `pg_restore --list`,
и в нём должна быть хотя бы одна таблица с данными. Если проверка не
прошла — каталог удаляется целиком, чтобы неполная копия не выглядела
свежей и годной.

Снять копию прямо сейчас:

```
bash /opt/gift/deploy/backup.sh
```

### Что таймер НЕ делает

Копии лежат на том же диске, что и база. От сбоя диска или потери
сервера они не спасают. Забирайте их к себе:

```
scp -r root@СЕРВЕР:/var/lib/gift/backups/ПОСЛЕДНЯЯ ./gift-backup/
```

Внутри лежит `.env` с ключом — храните этот каталог как пароль.

## 2. Ключ шифрования

Посмотреть текущий и сохранить вне сервера:

```
grep GIFT_SECRET_KEY /opt/gift/.env
```

Проверить, что ключ подходит ко всем секретам в базе:

```
gift-cli verify-key
```

Эта же проверка входит в `gift-cli doctor`. Если она ругается —
значит, `GIFT_SECRET_KEY` заменили руками, без перешифрования базы.
Бот при этом запустится, но площадки начнут отвечать 401. Лечение:
вернуть прежний ключ в `.env` и сменить его правильно (ниже).

### Смена ключа

Ключ меняют, если он мог утечь — например, `.env` попал в чат или в
чужие руки.

```
gift-cli rotate-key --dry-run     # показать, что будет перешифровано
gift-cli rotate-key               # сменить (новый ключ сгенерируется)
gift-cli rotate-key --new ВАШ_КЛЮЧ
```

Что происходит: все секреты расшифровываются старым ключом,
зашифровываются новым и записываются **одной транзакцией**. Если хоть
одно значение не читается старым ключом, не меняется ничего —
наполовину перешифрованная база хуже исходной. Новый ключ вписывается
в `.env`, факт смены попадает в журнал аудита.

После смены обязательно:

```
systemctl restart gift-web gift-bot gift-worker
```

Пока сервисы не перезапущены, они работают со старым ключом в памяти.

И сохраните новый ключ вне сервера — старые копии базы расшифровываются
**старым** ключом, новые **новым**. Ключ от копии должен лежать рядом
с копией.

## 3. Восстановление

```
bash /opt/gift/deploy/restore.sh /var/lib/gift/backups/20260914-033000
```

Скрипт останавливает сервисы, кладёт `.env` из копии (прежний сохраняет
как `.env.before-restore`), заливает дамп базы, возвращает сессии
Telegram и проверяет главное: расшифровываются ли секреты ключом из
копии. Сервисы намеренно не поднимает — сначала посмотрите
`gift-cli doctor`.

```
gift-cli doctor
systemctl start gift-bot gift-web gift-worker
```

### После восстановления проверьте режим торговли

Режим (SAFE / SEMI / AUTO), аварийный стоп и разрешения площадок
хранятся в базе и вернулись такими, какими были на момент копии. Если
копия снята, когда бот торговал в SEMI, он и продолжит в SEMI.
Откройте панель → «Торговля» и убедитесь, что состояние то, которое вы
ожидаете.

---

## 4. Восстановление на чистом сервере

1. Поставьте бота как обычно (`install.sh`) — он создаст пустую базу.
2. Скопируйте каталог копии на сервер.
3. Запустите `restore.sh` — он перезапишет и `.env`, и базу.
4. `gift-cli verify-key`, затем `gift-cli doctor`.

Порт панели и пути при этом берутся из восстановленного `.env`: если
на новом сервере они должны отличаться, поправьте `.env` после
восстановления и выполните `bash deploy/update.sh`.
